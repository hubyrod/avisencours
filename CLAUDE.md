# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`avis-en-cours`: queries a public OpenDataSoft (ODS v2.1) procurement portal REST API for currently-open SERVICES-type French public tenders (avis), then classifies each as **relevant** (mobility-planning consultancy studies), **travaux** (works — out of scope), or **excluded** (out-of-domain). Bun + TypeScript, no test suite, no build step.

It runs two ways: a **local CLI** (`src/index.ts`, writes markdown reports) and a **deployed service on Clever Cloud** (daily cron → PostgreSQL → French dashboard with passwordless email-code login + MailPace email digest). See README "Deployment" for the runbook.

## Commands

```bash
bun install                              # setup (also: cp .env.example .env and edit)
bun run src/index.ts                     # CLI run: fetch → classify → write markdown reports
bun run src/index.ts "mobilité OR vélo"  # custom OR-query (replaces default keyword list)
USE_CACHE=1 bun run src/index.ts         # re-classify from .cache/scrape.json, no API fetch (fast — use this when iterating on classifiers)
CLASSIFIER=regex USE_CACHE=1 bun run src/index.ts  # force classifier: regex | llm | hybrid
bun run run:daily                        # server-side daily job: fetch → Postgres → digest email (needs POSTGRESQL_ADDON_URI; always fetches fresh, no cache)
bun run start                            # dashboard server on :8080 (needs POSTGRESQL_ADDON_URI; set ADMIN_EMAILS to seed an admin)
bun run typecheck                        # tsc --noEmit
bun run lint                             # oxlint src
bun test                                 # unit tests (src/*.test.ts — pure logic only, no DB/network)
TEST_DATABASE_URL=postgresql://<user>@localhost:5432/avis_test bun test  # + integration tests (db, server, live) on a throwaway Postgres — this is what CI runs; skipped without the var
bun run build                            # bundling smoke check (bun build → dist/, gitignored)
bun run eval [--verbose] [model …]        # labelled set (eval/avis.jsonl) × candidate OpenRouter models → accuracy/cost/latency; --export dumps .cache/scrape.json for labelling
```

CI (`.github/workflows/ci.yml`) runs those four checks on every push/PR to `main` — the test step against a `postgres:16` service container with `TEST_DATABASE_URL` set, so the three `*.integration.test.ts` files gate the deploy too — then deploys to Clever Cloud (`clever deploy --alias server`, authenticated via `CLEVER_TOKEN`/`CLEVER_SECRET` repo secrets) and curls `/sante` until healthy. Pushing to `main` on GitHub = deploying to production.

`PORTAL_API_URL` and `PORTAL_DATASET` are required for anything that fetches (checked when the API URL is built, in `src/params.ts`). `OPENROUTER_API_KEY` is optional; without it the classifier falls back to `regex` (the config page shows a warning; a run that asked for llm/hybrid records a `warning` and mails `ALERT_RECIPIENT`). Email vars (`MAILPACE_API_TOKEN`…) are optional in dev — the daily job logs and skips emails, and login codes are printed to stderr instead of sent (in production working email is mandatory: login happens by emailed code). `OTP_PEPPER` is required in production (production = `DASHBOARD_URL` starts with `https://`). See `.env.example` for the full list.

A fresh (non-cached) run takes ~3 minutes and ~30 API calls for BOAMP, plus ~2–3 minutes and ~130 sequential requests for achatpublic.com (`ACHATPUBLIC=0` skips it) ~10 requests for AFD/dgMarket (`AFD=0`) and, per MPE site, one request per 20 rows plus one per retained row (Maximilien ~25, AMPA ~16; `MAXIMILIEN=0`, `AMPA=0`) and ~15 minutes for Marchés Online (~150 paced keyword pages plus one per retained notice; `MARCHESONLINE=0`); hybrid/llm modes send ~2 000 avis (~2.4 M prompt tokens) to the LLM, about 5 cents of OpenRouter credit per run with the default chain (cost/tokens/models are recorded per run in `runs.llm_stats`). Prefer `USE_CACHE=1` during development. For local DB testing, a throwaway Postgres database + `POSTGRESQL_ADDON_URI=postgresql://<user>@localhost:5432/<db>` works; tables are auto-created.

## Architecture

Shared pipeline in `src/pipeline.ts` (`runPipeline()`): scrape BOAMP (or load cache) → dedupe by `idweb` → drop attribution/résultat/annulation notices → append the secondary sources (achatpublic.com, AFD/dgMarket, the MPE sites Maximilien and AMPA, Marchés Online — each non-blocking, its failure becomes a run `warning`) → classify each avis into relevant/travaux/excluded. Two consumers:

- `src/index.ts` (CLI) — writes two timestamped markdown reports (`avis-en-cours-<stamp>.md`, `avis-travaux-<stamp>.md`; gitignored). Excluded avis only go to stderr with their reason, followed by the LLM stats block.
- `src/run.ts` (daily job, fired by `clevercloud/cron.json` → `daily-run.sh`) — takes a Postgres advisory lock (skips if a run is in flight), records a row in `runs`, loads the editable config from the DB (`search_keywords` → the OR-query, `scope_rules` → forced keep/exclude, `settings` → classifier mode / digest window / départements; DB values beat env, empty keyword table falls back to `defaults.ts`), upserts every avis into `announcements` (`ON CONFLICT (idweb)` updates everything except `first_seen_*`), then sends the MailPace digest ("new" = first seen since the last run with `digest_sent = true`; sent daily even when empty, as a heartbeat). Digest recipients = users who opted in via `receive_digest` (default false, toggled on `/profil`). The digest itself goes out every day to those recipients, even when there is nothing new (subject « pas de nouvel avis »). `SKIP_DIGEST=1` (set by the dashboard's « Relancer maintenant » button, which spawns `bun src/run.ts` as a child of the web process — a redeploy or instance restart kills it mid-way; liveness = the Postgres advisory lock (`isRunLockHeld()` reads `pg_locks` for `RUN_LOCK_ID`) **and** a fresh heartbeat (`runs.progress.updatedAt`, written by the job at least every 2 s while active; `heartbeatStale()` = older than `HEARTBEAT_STALE_MS`, 10 min, falling back to `started_at` when there is no progress yet). A killed process leaves a zombie Postgres session holding the lock for up to ~35 min (seen on 2026-09-18), so lock alone is not proof of life: `runInFlight()` in `server.ts` terminates the lock holder (`terminateRunLockHolders()`) when the heartbeat is stale, then closes the row via `closeOrphanRuns()`; `run.ts` does the same before giving up when `tryAcquireRunLock()` fails; `startRun()` closes leftovers under the lock; `RUN_STALE_MS` (1 h) is only the fallback when `pg_locks` cannot be read) skips the digest without marking `digest_sent`, so manual-run finds still appear in the next morning's email. On failure: run marked `error` + alert email to `ALERT_RECIPIENT`.

`src/server.ts` serves the dashboard: "current" tenders = `last_seen_run_id` = latest successful run AND deadline not passed, sorted by deadline; "Nouveau" badge = first seen in that run. Each avis has a detail page (`/avis/:idweb`) with a comment thread (`comments` table; authors or admins can delete; comments cascade with the avis, survive author deletion as « utilisateur supprimé ») and a collaborative **status** (« à évaluer », « répondu », « gagné »… — any user can change it). The status list is admin-editable on `/admin` (`statuses` table: label, color, position, `is_rejet` = hideable on the dashboard, archive-only — no delete, `ON DELETE RESTRICT` backstop); each change is an append-only row in `status_events` shown inline in the thread; current status = latest event, no event = the lowest-position active status (implicit, no row). The dashboard shows a status badge per row plus a filter (`?statut=<id>`, `?masquer=1`); filtering on the default status also matches event-less avis. `/configuration` (route tier `config` = admins + users with the `can_configure` flag, delegated from `/admin`) edits the pipeline config live, in two tabs (`?onglet=resultats`, the default, and `?onglet=moteur`; `configPage(user, onglet, notice)`): **Résultats** = what decides the avis and what the team receives — search keywords (last one can't be deleted; ` OR ` rejected inside a term), « toujours garder / toujours exclure » rules (pure pre-classifier substring matches in `src/rules.ts` — garder wins), départements, digest window; **Moteur** = how the watch is produced — the update card (live progress, recap, rate-limited « Relancer maintenant » that spawns `bun src/run.ts` with `SKIP_DIGEST=1`), the sources card, the classification card (classifier mode + LLM chain + OpenRouter credit + last run cost). Every card states its effect (`.effet`). All settings cards POST to `/configuration/reglages`; `handleSettingsUpdate` validates and writes only the fields present in the form, then redirects to the card's tab and anchor (`configUrl(onglet, carte)`); errors re-render the same tab. Routes with `:param` segments are matched by `src/router.ts`. `/sante` is public health JSON; everything else requires login.

**Live threads** (`src/live.ts`, JS-required): comment threads (comments + status events interleaved) are reactive via the Skip Framework running in-process as WASM (`runService`, internal ports 9080 streaming / 9081 control — they bind 0.0.0.0 but only `PORT` is exposed by the Clever LB). `@skip-adapter/postgres` watches `comments` + `users` + `status_events` + `statuses` + `runs` through LISTEN/NOTIFY triggers it installs itself (orphans are purged at boot — `cleanupOrphanTriggers` hardcodes that table list; extend it when watching a new table); *writes stay plain SQL* in `db.ts`. The graph: all tables mounted with **TEXT keys** (bigint keys fork string/number in the adapter — never use numeric key types), per-row mappers turn comments and status events into a common `ThreadItem` shape (author-joined; events also join `statuses`, so admin renames propagate live), `merge`d then folded by a `ThreadSorter` mapper (key = `idweb`, value = full sorted thread), one `thread` resource; `runs` rows become a `RunView` (`runToView`: id, status, dates, progress) behind a `run` resource keyed by the run id (string). The browser opens `EventSource("/avis/:idweb/commentaires/flux")` or `EventSource("/mise-a-jour/:id/flux")` — authed routes that call `resourceStream()` (`commentStream`/`runStream` wrappers): mint the stream UUID on the control port, pipe the Skip SSE stream through (25s heartbeats for the LB; `DELETE /v1/streams/<uuid>` on disconnect or the WASM subscriber graph leaks). For runs the event is only a *change signal*: `PROGRESS_JS` then fetches `/mise-a-jour/:id/fragment` (JSON `{ running, card, banner }`, rendered server-side through `runInFlight`) and swaps it into `#maj-carte` (configuration) or `#bandeau-maj` (dashboard); `running: false` → one `location.reload()`; flux error before `init` → 15 s reload fallback, and `<noscript>` keeps a meta refresh. The detail page renders the thread client-side from the `init` event; forms POST via fetch and return JSON. Skip failing to boot is non-fatal: the flux route 503s and the page shows « Commentaires indisponibles ». These are the repo's only runtime npm deps (`@skipruntime/*` + `@skip-adapter/postgres`, pinned 0.0.23 with a local reconnect patch in `patches/` — upstream's adapter still has no reconnect; to bump, edit the versions, `bun patch @skip-adapter/postgres@<v>`, apply the old patch with `patch -p1` inside the package dir, delete the `.orig` files it leaves, `bun patch --commit`). The adapter connection is tagged `application_name = avis-live` (`LIVE_APP_NAME`); `liveAdapterState()` (`/sante` → `livePg`) reports `connected` + `watched` (tables whose LISTEN is live — 5 when healthy, 0 during a reconnect). Known limit of the patch: on reconnect each table is re-synced (full SELECT) *before* its LISTEN is re-issued, so a write landing in that gap is missed until the next change on that key. **`run.ts` and `db.ts` must never import `live.ts`** (the cron job must not open an adapter LISTEN connection or load WASM); `bun run build` needs `--packages external` for the same packages. `LIVE_COMMENTS=0` disables the engine.

**Integration tests** (`src/*.integration.test.ts`): run only when `TEST_DATABASE_URL` points at a throwaway Postgres (`createdb avis_test`); CI provides one, so they gate every deploy. `db.integration` covers what unit tests cannot see (the jsonb shape actually stored for `runs.llm_stats` and its migration, the advisory lock via a second connection, `startRun` closing orphaned `running` rows, `getCurrent` source/famille filters and `countCurrentBySource`). `server.integration` spawns the real `bun src/server.ts` on port 18089 against that DB (`LIVE_COMMENTS=0`, `ACHATPUBLIC=0`), logs in through the dev login code printed on stderr, and checks `/sante`, the dashboard (badges, `?source=`, `?famille=`), `/configuration` (sources card, LLM stats line, an orphaned run being closed) and `/avis/:idweb` — add a case there whenever a page breaks in production. `live.integration` covers the Skip engine — run it before touching the Skip packages, the patch, or `live.ts`. Two layers: the adapter alone on a scratch table (init sync, NOTIFY, then `pg_terminate_backend` of the LISTEN connection → reconnect, resync, notifications again, no duplicates), and the full engine (`startLive` + `commentStream` on the real schema: init/update SSE events for comments, status events and a status rename, a kill of the `avis-live` connection, deletion, a second subscriber, an unknown idweb). They use ports 19080/19081 and truncate `comments`, `status_events`, `announcements`, `runs`, `users`, `statuses` in that DB.

**Auth** (`src/auth.ts`, modeled on Hugo's `chambre` project): passwordless — users request a 6-digit code by email (`/connexion`), codes are HMAC-peppered (`OTP_PEPPER`), 5-min TTL, max 5 attempts, 60s resend gate, anti-enumeration (same response whether the account exists). Sessions are opaque tokens (SHA-256 hash stored in `sessions`, raw token only in the cookie — `__Host-session`, HttpOnly, SameSite=Lax, 30-day rolling expiry with 1h-throttled touch). Accounts are admin-created (`/admin`, `is_admin` flag) or auto-provisioned at first login for emails on `ALLOWED_EMAIL_DOMAINS` (comma-separated, exact domain match, never admin); `ADMIN_EMAILS` env is upserted as admin at startup (grant-only). CSRF = SameSite=Lax + Origin-header check on POST. Rate limits are in-memory (fine: 1 instance). **Run progress** (`src/progress.ts`): `run.ts` builds a `ProgressTracker` with one step per entry of `SOURCES` (disabled ones end up `skipped`), then `classify`, then `digest`, and passes it to `runPipeline({ progress })`; the pipeline calls `start/advance/finish/fail/skip` around BOAMP (`scrapeAll`'s `onPage` now also gives the total page count), each secondary source (every scraper takes an optional `onPage(done, total)` next to `log`) and the classification counter; `run.ts` marks `digest`. Every state change — and counters at most every 2 s — is written to `runs.progress` (jsonb, `updateRunProgress`, errors logged and ignored; a final exact snapshot is written before `finishRun`). Pages read it with the run row (`normalizeProgress` in `toRunRow`): `/configuration` renders `renderProgress()` inside `renderRunCard()` (milestone list + bar while in flight, compact recap afterwards), the dashboard banner shows `summarizeProgress()`, `/sante` exposes `lastRun.progress`; while a run is in flight both pages update in place through the Skip `run` resource (see Live threads), otherwise a 15 s reload fallback. Liveness is still the advisory lock, progress is informational only. The CLI passes no tracker.

`src/db.ts` holds the schema (11 tables: `runs` (with `llm_stats`, `warning`, `progress` jsonb), `announcements`, `users`, `sessions`, `email_verification_codes`, `comments`, `statuses`, `status_events`, `search_keywords`, `scope_rules`, `settings`), created idempotently at startup — there is no separate migration system. DB access uses Bun's built-in `Bun.sql` (the Skip packages for live comments are the only runtime npm deps). Deadline is stored both as text (`deadline_text`, the scraper's `dd/mm/yyyy à HHhMM` format) and parsed (`deadline` timestamptz, parsed back from that text in `db.ts`).

- `src/params.ts` — builds the ODS v2.1 URL: keyword OR-query becomes a `where=` clause of `search(*, "...")` expressions, ANDed with a date filter (`datelimitereponse >= today`, falling back to `datefindiffusion` when no deadline).
- `src/scraper.ts` — paginated fetch (100/page), maps ODS records to `Announcement`. The `raw` field concatenates objet + nested JSON fields (`donnees`, `gestion`) + buyer/type/procedure — classifiers match against `raw`, not just `objet`.
- `src/classify.ts` — regex classifier. Order matters: hard exclusions (contrôle de travaux, contrôle qualité de service, télécom, VRD) → the large `EXCLUDE_HORS_DOMAINE` list → `isAMOForWorks` (AMO + works-verb + infra-noun ⇒ travaux) → `TRAVAUX` patterns → default relevant. All matching is on accent-stripped lowercase text (see `normalize`), so write patterns without accents.
- `src/classify-llm.ts` — prompt (French system prompt + few-shot, tuned on mistral-small) and a thin `classifyLLM(a, ctx)` over `src/llm.ts`. `LlmContext` (chain, `LlmStats`, `Breaker`) is built once per run in `pipeline.ts`.
- `src/llm.ts` — OpenRouter client, no SDK. One request carries the whole chain (`models: [...]`, server-side fallback on outage / rate limit / moderation / context), `provider: { sort: "price", require_parameters: true, max_price }`, `response_format: json_object`, `usage: { include: true }` (cost in USD). Client side: retries via `src/http.ts` (timeouts and network errors too; 503 at most twice; 2 attempts when the chain has >1 model, 4 otherwise), one rotation (`models.slice(1)`) when a 200 reply is unusable (bad JSON, empty, `finish_reason: length`, invalid category), never on HTTP errors. 401/402 → `LlmAuthError`. `Breaker` trips on `LlmAuthError` or 5 consecutive chain failures, aborts in-flight requests, and the pipeline classifies the rest of the run by regex; `run.ts` then records `runs.warning`, mails the alert, and skips the digest without marking `digest_sent`. Model chain precedence: DB setting `llm_models` > `LLM_MODELS` env > `DEFAULT_LLM_MODELS` (`defaults.ts`: mistral-nemo, cheapest in the catalog and 39/40 on `bun run eval`, then mistral-small-24b-2501, then llama-3.1-8b). `Classification.classifier` / `announcements.classifier` = `regex` | `regle` | `erreur` | model id.
- `src/openrouter-catalog.ts` — public `GET /models` (cached 1h, 5s timeout, server only, never from `run.ts`): validates the chain on save (unknown id, no JSON mode), feeds the datalist with prices on `/configuration`; `GET /auth/key` shows remaining credit. Catalog unreachable = syntactic validation only, never blocks.
- `src/classify-hybrid.ts` — regex first; only avis the regex leaves as `relevant` go to the LLM. Default mode when `OPENROUTER_API_KEY` is set.
- LLM/hybrid classification runs at concurrency 5; a per-item classification error defaults the avis to `relevant` ("revue manuelle") rather than dropping it.

**Second source — achatpublic.com** (`src/achatpublic.ts`): no API. The scraper replays the public "entreprise" search form (`POST rechercheCsl.action`, ISO-8859-15 form, `searchCslBean.marche` 1=fournitures/2=services, `searchCslBean.page` = **0-based absolute page index**, 10 cards per page, session cookie `PROD_APC_ID`), with an empty keyword so every open consultation of a nature is listed (~90 pages services + ~35 fournitures ≈ 2–3 min per run), then filters locally with `matchKeywords` (`src/familles.ts`: start-of-word match on normalized title; uppercase sigles and ≤4-char terms match a whole word + optional plural — the site's own search is a bare substring match, `vélo` ⊂ `développement`). Detail pages (`ficheCsl.action?PCSLID=…`, public, no cookie) are fetched only for retained cards (description, CPV, opening date). `idweb` = the PCSLID (`CSL_2026_…`, may contain `-`), `source = "achatpublic"`. Families (`ACHATPUBLIC_SEARCHES` in `defaults.ts`, taken from the client's manual watch procedure): `mobilité` (services → normal regex/LLM classifiers), `kiomda` (fournitures: counters/sensors, kept only with a bike/pedestrian/traffic word), `inondations` (services: AMC/PAPI/GEMAPI studies, kept unless works). `classifyFamille` runs before the classifiers for non-mobility families and never calls the LLM. The source is non-blocking: failure → `warning` on the run (alert email « mise à jour partielle »), BOAMP results kept. `ACHATPUBLIC=0` disables it. The keyword lists are code-only for now (not in `/configuration`). `announcements.source` / `announcements.famille` columns; dashboard `?famille=` filter + badges; `src/departements.ts` maps the « Lieu d'exécution » label to codes (more than 15 codes = « France entière », kept by the département filter). When achatpublic changes its HTML, `parseCards` throws on an empty first page, which surfaces as the warning.

**Third source — AFD on dgMarket** (`src/afd.ts`): `afd.dgmarket.com/tenders/brandedNoticeList.do`, POST with `sub=15` (category « Transports », the `catId` from the advanced search; the `CpvCatBean: …` option value the form shows is *not* accepted) and `status=live`, 20 rows per page, next page = the « Suivant » link. No account needed: list, filter and full notice text (`/tender/<id>`) are public; only `biddingDocumentsList.do` needs a subscription. The first GET is redirected 3 times (`web3-login.dgmarket.com/um~user/login.do?autoLogin=true` → `newSession.do` → back) and each hop sets cookies on a different domain, so `CookieJar` keeps cookies per domain and `Session.request` follows redirects manually (a 240-byte « requires digi_session_id » body means the cookies were lost). Dates come as « Sept 17, 2026 » / « Aou 31, 2026 » / « Octobre 2, 2026 - 12:00 » (English or French month names) → `parseAfdDate`. `idweb = AFD-<noticeId>`, `source = "afd"`, `famille = "mobilité"` (normal classifiers; notices are abroad, often in English), `department` = country name (passes the département filter), `typeAvis = "AFD — <type>"` so « Attribution de contrat » notices are dropped by the pipeline's `keep()`. The list announces more notices than it renders (e.g. « 1-6 de 6 » with 4 rows: restricted notices are counted but hidden) — not an error. `AFD=0` disables it. Adding another secondary source = one entry in the `sources` array of `loadAll()` in `pipeline.ts`, a `Source` value in `scraper.ts`, and an entry in `SOURCES` (`src/sources.ts`: label, URL, one-line description, env kill switch — the registry drives `isSourceEnabled` in the pipeline, the dashboard `?source=` filter with per-source counts (`countCurrentBySource`), the source badge on every row, and the « Sources de veille » card on `/configuration` which shows active / désactivée / en échec — « en échec » = the last run's `warning` mentions the source label, so warnings must keep using `sourceLabel()`).

**atexo MPE sites** (`src/mpe.ts`, registry `MPE_SITES`: Maximilien `marches.maximilien.fr` (~450 open rows), AMPA `demat-ampa.fr` (~300); `marches-publics.gouv.fr` (PLACE, ~2 100 rows, ~106 pages) is the same software and would be one more entry): `<base>/?page=Entreprise.EntrepriseAdvancedSearch&AllCons` lists every open consultation (public, no account). PRADO framework: 20 rows per page (`listePageSizeTop=20`), the next page is a POST to the same URL with `PRADO_POSTBACK_TARGET=ctl0$CONTENU_PAGE$resultSearch$PagerTop$ctl2`, the `PRADO_PAGESTATE` hidden field of the page just received, and the session cookie (without the cookie: HTTP 400). Rows carry everything but the CPV: `refCons`/`orgCons` hidden inputs, procedure, category, publication date and deadline as day/month/year blocks (`parseRows`, `dateBlock`), intitulé/objet/organisme in `title=` tooltips, lieux d'exécution as « (75) Paris, (77) … » (`departementsFromLieux`, >15 codes = « France entière »). Detail = `/entreprise/consultation/<id>?orgAcronyme=<org>` (public), read only for retained rows (`parseFiche`: type d'annonce, CPV, full objet). Local filter: category « Services » + `MPE_SEARCHES` (`defaults.ts`, the client's keyword list, split into mobilité and inondations families). `idweb = <site.prefix><refCons>` (`MX-`, `AMPA-`), `source` = the site's. `src/mois.ts` is the shared month-name parser. Each site has an env kill switch (`site.env`: `MAXIMILIEN=0`, `AMPA=0`).

**Marchés Online** (`src/marchesonline.ts`, marchesonline.com, Le Moniteur): the site's own "profils de recherche" and alerts need an account (max 5 profiles without subscription), but the keyword pages `/appels-offres/top-recherches/<slug>` (`keywordSlug`: accents stripped, spaces → `-`; `?page=N`, 20 cards per page, count in « : 176 avis », « Aucun avis pour cette recherche » past the end) and the notice pages are public. The scraper walks every distinct keyword of `MARCHESONLINE_SEARCHES` (`defaults.ts`: the client's five profiles merged into mobilité, plus kiomda counters (compteur/capteur/boucle/pyroélectrique/piézoélectrique) and inondations; ~4 400 cards with overlap, ~250 pages, "transport" and "échange" alone are ~100 pages — the site's search is lexical/stemmed, so `matchKeywords` re-filters titles at start of word), dedupes by numeric id (`ao-<id>-<version>` in the link, `idweb = MO-<id>`), filters the nature on the card's activity label (`natureMatches`: services ⇒ Services / Etudes, Maîtrise d'oeuvre, Contrôle / Assistance / Concours / Autres; fournitures ⇒ Fournitures), and reads the detail (`id="print_area"` → « Descriptif » text, first 3 000 chars, CPV) only for retained cards. Cards carry the old markup as an HTML comment: `parseCards` strips comments first. The detail is skipped when the regex classifier already excludes the title alone (most « transport » hits: autocars, scolaire, déchets), and the site's activity label « Etudes, Maîtrise d'oeuvre, Contrôle » is shortened to « Études » before entering `raw`/`typeAvis` (the raw label would trip the `maitrise d'oeuvre` travaux pattern on every study). The site sits behind Cloudflare and blocks the IP (429 with `cf-mitigated: challenge`, for many minutes) after a few hundred quick requests: `get` pauses 1.2 s between requests and backs off on 429 (Retry-After or 30 s × attempt), and `maxPagesPerKeyword` (default 8, pages are newest-first) caps the wide keywords (« transport », « échange » would be ~50 pages each) — so an old notice beyond the cap drops out of « current » even if still open. ~150 list pages + ~250 detail pages ≈ 15 min per run (2026-09-18 probe: 1 975 distinct cards, 348 retained, 247 details), by far the slowest source; the daily run holds its advisory lock for the duration. Deadline is a date without time. `MARCHESONLINE=0` disables it.

## Domain scope (what "relevant" means)

The client is a mobility-planning consultancy that does **studies only**: plans de mobilité, schémas directeurs (cyclable, piéton), traffic modelling, parking/circulation studies, socio-economic evaluation, AMO for elaborating plans/studies. Not in scope: any works (MOE, construction), AMO tied to building a physical structure, transport operation (DSP, autocars, transport scolaire), telecom (never confuse "mobilité" with mobile phones), VRD, operational service-quality audits.

When adjusting scope, three files must stay consistent: the `KEYWORDS` search list in `src/defaults.ts`, the regex rules in `src/classify.ts`, and the LLM system prompt + few-shot examples in `src/classify-llm.ts`. A scope change usually touches at least the last two.
